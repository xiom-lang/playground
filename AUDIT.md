# XIOM Playground -- Audit (2026-09-18)

Auditor: Kilo (debug session). Scope: the `playground` repository only.
DevOps/VPS work (`xiom-lang/ops`, Hestia, Docker host) is owned by the ops
session and is only referenced where the playground depends on it.

## 0. Executive summary

The live playground runs, but it is shipping a compiler/stdlib from a
different era than its lessons, and the server has several real bugs that
happen to be masked by the current low traffic.

- **Lessons are stale against the toolchain.** Against the released v0.60.1
  toolchain: **185/410 solutions fail to type check**, **67/410 templates
  fail**, and of the 213 that type check, **17 fail in codegen** because of
  compiler bugs (enums with payloads, Vec-by-reference, interface dispatch).
  Only 196/410 lessons both compile and run today.
- **The server is one slow submission away from failure.** Compiles are
  serialized through `spawnSync` (one compile blocks the whole process and
  the healthcheck), the 15 s timeout is below the measured p99 for real
  lessons, and the server writes every submission to `os.tmpdir()` root,
  which makes the compiler recursively index the entire temp directory
  (measured 15-18 s on a large temp tree vs 0.6 s in a clean work dir).
- **`/api/format` is broken** in production: the v0.60.1 CLI has no `fmt`
  subcommand, but `js/app.js` calls the endpoint.
- **Version metadata is inconsistent everywhere** (v0.49.9 / v0.50.0 /
  v0.58.0 / v0.60.0 / v0.60.1 all appear in the same repo) and nothing in
  this repo tracks, verifies, or automates the toolchain/stdlib/WASM
  versions. The ops deploy script already tracks `latest.json`; the
  playground itself has no pin, no CI, and no lesson compile gate.
- **Security: path traversal in the static file handler** - a raw
  `GET /../../xiom-lang/xiom/STDLIB_VERSION` returns file contents from
  outside the served root (verified, 200 OK).

Everything below includes evidence and a recommended fix. All code changes
are deferred; this document is analysis only.

### 3.4 Encoding failures (12 lessons)

These files contain Windows-1252 bytes (`0x97` em dash, `0xD7`) and are not
valid UTF-8. The browser shows replacement characters; my Python sweep
could not decode them. Repo rule in `DEPLOY.md` says "Pure ASCII files
only", and commit `f808f71` claimed to strip mojibake, so these are
regressions.

`L2-21`, `L2-22`, `L2-23`, `L2-24`, `L2-25`, `L2-30`, `L2-41`, `L2-42`,
`L2-43`, `L2-44`, `L2-45`, `L2-59` (all `lessons/L2-data/...`).

Fix: convert to UTF-8 (or ASCII escapes) and add a CI check that every
lesson file decodes as UTF-8 and is pure ASCII.

### 3.5 Imports

Across all 410 lessons only three imports appear: `xiom.io` (398),
`xiom.string` (132), `xiom.math` (11). All three modules exist in the
released stdlib, so the *import mechanism* works; the problems are names
inside those modules and unimported modules (`xiom.rand`). No missing
`use` statements were found in the sense of "module does not exist", but
several lessons call names that moved to `xiom.convert`/`xiom.rand`.

### 3.6 Templates

67 templates fail. They fail for the same syntax reasons (`type X {`,
`mod`, enum `;`, old receivers) but are otherwise much healthier than the
solutions (L0/L1/L2 templates all pass). Fixing syntax in templates is
mostly mechanical and will remove most "the starting code does not
compile" cases.

## 4. Playground server and frontend bugs

Severity: H = user-visible/broken or a security issue, M = production
risk, L = hygiene.

### P1 (H, security) Static handler allows path traversal

`server.js:238-239` does `path.join(SCRIPT_DIR, req.url)` with no
containment check. Verified against a local instance:

```
GET /../../xiom-lang/xiom/STDLIB_VERSION -> HTTP/1.1 200 OK, body "stdlib-v0.60.0"
```

In the container this exposes any readable file (`/etc/passwd`,
`/toolchain/lib/**`), made worse by P15 (no `.dockerignore`, so `.git`,
`.kilo/` and `tools/` are inside the image). Fix: allowlist served paths,
`path.resolve` and verify the result starts with `SCRIPT_DIR`; reject
requests containing `..` or `%2e%2e`; return 404.

### P2 (H) One compile blocks the whole server

`runXiom` uses `spawnSync` (`server.js:49-56`) on Node's single thread.
Measured: two parallel POSTs (one check, one compile) took 15.0 s + 15.0 s
with total wall time **30.0 s** - perfect serialization. While a compile
runs, `/api/lessons` and the Docker healthcheck (5 s timeout) cannot be
served. Fix: `child_process.spawn` + `Promise`, with a concurrency
semaphore (2-4) and a queue; keep per-request timeouts.

### P3 (H) Temp workspace triggers a full temp-directory scan on every compile

The compiler adds the source's **parent directory** as a module catalog
root and recursively indexes it; the grandparent is indexed when it
contains any `.xi` file at its top level. `server.js:59`, `:130`, `:162`,
`:198` write submissions directly to `os.tmpdir()` root, so every compile
walks the whole temp tree.

Measured (Windows, released toolchain):

| Source location | `--check` |
|---|---|
| `%TEMP%\kilo\audit_iso\deep\prog.xi` (clean grandparent) | 0.58 s |
| `%TEMP%\kilo\audit_work\prog.xi` (grandparent has top-level `.xi`) | 16.1 s |
| `%TEMP%\prog_root.xi` (parent = temp root) | 18.3 s |

`%TEMP%\kilo` contained 1,859 top-level `.xi` files and 207,566 files in
total. On Windows this alone exceeded the server's 15 s timeout, so
`/api/compile` returned "Compilation failed" for a hello world. The
container's `/tmp` is smaller today, but it grows without bound (P8) and
the same mechanism applies.

Fix: create one subdirectory per request, e.g.
`<tmp>/xiom_pg/<hash>/prog.xi`, and delete it afterwards. Then parent is
tiny and grandparent is `.xi`-free. This also removes a cross-submission
module-resolution hazard (a stale `.xi` in temp can be picked up as a
module by another user's compile).

### P4 (H) `/api/format` is broken

`server.js:134` runs `xiom fmt <file>`; v0.60.1 has no `fmt`/`format`
subcommand. Verified on Linux:

```
$ xiom fmt p.xi      -> error: cannot read 'fmt': No such file or directory
$ xiom format p.xi   -> error: cannot read 'format': ... (same)
$ xiom --fmt p.xi    -> compiles normally (flag ignored), exit 0
```

The frontend calls it (`js/app.js:118`). Options: wire `xiom-fmt` into
the compiler CLI and keep the endpoint (preferred), or remove the button
until then. Do not ship an endpoint that always errors.

### P5 (M) The custom binary cache never populates and is redundant

`server.js:107-112` warms `CACHE_DIR` with
`xiom build <file> -o <cachedExe>`. `build` is a project subcommand: with
a positional file it treats `build` itself as a source path and fails
(`error: cannot read 'build'`). The failure branch deletes a file that was
never created, so `CACHE_DIR` stays empty forever and every request
recompiles. Meanwhile the compiler already has a content-addressed script
cache (`xiom run` warm = **0.004 s**, tested). Fix: delete the custom
cache and rely on the compiler cache, or warm with `xiom -o <cachedExe>
<file>` if a copy outside the compiler cache is really wanted.

### P6 (M) 15 s compile timeout is below the real p99

Measured on the release artifact (Linux, WSL, 6-way concurrency):

```
check: p50 297 ms, p90 633 ms, p99 1.6 s, max 1.9 s
run:   p50 3.9 s,  p90 8.5 s,  p99 10.4 s, max 11.4 s (L1-49)
```

`runXiom` timeout is 15 s (`server.js:51`), and a slower VPS plus P3
overhead can cross it; the code then reports "Compilation failed" with no
distinction from a genuine error. Fix: raise to 30 s after P3, surface a
dedicated "timed out" message, and pass the compiler's own `--timeout`
where supported.

### P7 (M) Temp file name collisions

`xiom_pg_${Date.now()}.xi`, `xiom_chk_${Date.now()}.xi`,
`xiom_lazy_${Date.now()}.xi` (`server.js:59`, `:130`, `:162`, `:198`)
collide for two requests in the same millisecond; the second write
overwrites the first and both `finally` blocks delete the file. Fix: use
the cache hash or `crypto.randomUUID()`.

### P8 (M) Unbounded temp growth

`CACHE_DIR` (`server.js:14`) has no eviction; the compiler's own
`<temp>/xiom_jit` cache caps at 100 MB (`xiom` `jit.rs`), but the server
does not. On the container's 256 MB tmpfs, cached binaries plus compiler
artifacts eventually fill `/tmp` and compiles start failing. Fix: LRU
eviction or drop the server cache (P5); combine with P3's per-request
cleanup.

### P9 (M) No request body limit

`parseBody` (`server.js:144-150`) concatenates the entire body with no
cap. A single large POST can consume the container's 768 MB memory limit
or wedge the event loop. Fix: reject bodies over e.g. 512 KB with 413.

### P10 (L) Unneeded CORS wildcard

`server.js:153` sets `Access-Control-Allow-Origin: *` on every response.
The playground is same-origin; drop it (or restrict to the site origin).

### P11 (L) Stale version strings and UI claims

See section 2. Every one should come from a single generated value:
toolchain tag (from `latest.json` / deploy), stdlib version, WASM version.

### P12 (M) WASM/server check race and stale WASM compiler

`js/compiler.js:26-93`: `wasmCompiled` is set in a promise callback, but
the `if (!wasmCompiled)` fetch is issued synchronously, so `/api/check` is
always sent; the two diagnostic renderers can then overwrite each other.
The bundled WASM is v0.58.0 while the server is v0.60.1, so pure programs
can get different diagnostics from each path. Fix: `await window.xiomWasm`
once at startup, prefer one source of truth (WASM for pure programs, server
otherwise), and refresh the WASM bundle from a release asset (C8).

### P13 (L) Docs and legacy code are stale

- `README.md` references `xiom.wasm` and `xiom_v0.49.9.wasm` (absent), and
  advertises `server.py` as an alternative. `server.py` is the v0.49.9
  pipeline and implements none of the current endpoints (`/api/check`,
  `/api/tokens`, `/api/ir`, `/api/format`, `/api/lessons`); the frontend
  cannot work against it. Delete or rewrite it.
- `docs/PLAYGROUND_SPEC.md` still describes the v0.49.9 -> v2.0 plan.
- `DEPLOY.md` points at `xiom-lang/.github/scripts/...`; the scripts moved
  to `xiom-lang/ops/scripts/` (ops-owned, noted only).

### P14 (M) Stdlib reference panel is drastically stale

`js/stdlib-ref.js` is hand-maintained: 20 modules / 594 entries, footer
says "64 modules / ~2,215 functions", `index.html` says "20 stdlib
modules". Released stdlib: **516 modules, 6,497 `pub fn`, 395 type
declarations**. The panel cannot be maintained by hand. Fix: add
`tools/generate-stdlib-ref.js` that parses `<toolchain>/lib/xiom/**/*.xi`
for public items and regenerates the data file (plus the module count in
the UI); run it in the release/validation pipeline.

### P15 (L) No `.dockerignore`

`Dockerfile` does `COPY . .`, so the image contains `.git`, `.kilo/`
(worktrees, 5.3 MB), `tools/`, `docs/`. Combined with P1 this is an
information exposure; it also bloats the image. Add a `.dockerignore`
(`.git`, `.kilo`, `tools`, `docs`, `*.md`, `server.py`, `playground.code-workspace`).

### P16 (M) Warnings are reported as errors

`parseDiagnostics` (`server.js:39-47`) treats any line starting with
`warning` as `{ kind: 'error', code: 'E001' }`, and the `[CODE]` regex does
not match the current `warning[W001]:` format. Catalog warnings therefore
show up in the Diagnostics tab as errors. Fix: parse `^(warning|error)\[(\w+)\]`,
set `kind` accordingly, and ignore the collision-continuation lines.

### P17 (L) Flag hygiene

`/api/check` sends `--check --check-only`; `--check-only` is not a
recognized flag (harmless no-op, but relies on ignored args). Use `--check`
alone, and consider `--check --diagnostics=json` so the server stops
regex-parsing human output. The docs and `server.js` banner still say
"multi-stage", but `/api/compile` only runs `xiom run`; tokens/IR come from
the lazy endpoints. Align the wording.

## 5. Performance analysis and recommended compiler modes

What exists in v0.60.1 and what the playground uses:

| Flag | Purpose | Used by playground? |
|---|---|---|
| `--check` | type check only (no codegen) | yes (`/api/check`) |
| `run <file>` | script mode: implicit main, compile, run, script cache | yes (`/api/compile`) |
| `--incremental` | IR cache for unchanged sources | no |
| `--parallel` / `--jobs N` | parallel lex+parse | no |
| `--parallel-codegen` | parallel per-function IR | no |
| `--opt-level 0..3` | clang opt level (default -O2 floor) | no |
| `--cache` | binary cache for `--run` | no |
| `--timeout`, `--max-memory-mb` | compiler watchdogs | no |
| `--diagnostics=json` | machine-readable diagnostics | no |

Important: **script mode (`xiom run`) ignores almost all of these flags**
(finding C3). The `run` branch in `main.rs` builds a default
`CompileConfig` before the flags are parsed, so adding `--parallel` etc.
to `server.js` would have no effect today. Two options:

1. Compiler-side: make `run` honor `--opt-level`, `--incremental`,
   `--parallel`, `--jobs`, `--timeout`, `--max-memory-mb`,
   `--diagnostics=json`.
2. Playground-side, if lessons/users always provide `fn main`:
   invoke `xiom --run --opt-level 0 ... <file>` (non-script mode honors
   flags) with a script-mode fallback when `fn main` is absent.

Measured (Linux, release artifact, single valid program):

```
script run cold        2.99 s      script run warm (cache)  0.004 s
-o compile default     6.54 s*     -o --opt-level 0         0.95 s*
-o --parallel          3.00 s      -o --incremental         3.12 s
```

(*) first-run noise; treat as directional only. The safe, high-value
changes for the app are, in order: P3 (remove the temp scan, -15 s on
Windows), P2 (async + queue so one compile cannot stall the site), P5
(remove the dead cache double-compile), then use `--check` for checking
(already done) and the compiler script cache for repeats (already done).
Lowering the opt level is optional and should be gated on a correctness
sweep, because the compiler's own docs note historical -O0/-O1
miscompiles.

Run-time budget check: the server's 15 s timeout is shorter than the
measured p99 of 10.4 s plus P3 overhead, so P3/P2/P6 are prerequisites for
comfortable headroom.

## 6. Versioning automation (requested)

Single source of truth: `https://dl.xiom-lang.org/latest.json`
`{ "tag": "v0.60.1", "published": ..., "assets": [...] }`. The ops deploy
script already uses it for `/opt/xiom/toolchain` (`.mirror-tag`); the
playground repo should consume the same data instead of hardcoding.

Proposed pieces (all new files, no behavior change until wired):

1. **`TOOLCHAIN_VERSION`** at repo root - the tag the lessons are verified
   against (e.g. `v0.60.1`). `tools/fetch-toolchain.ps1|.sh` reads it,
   downloads the matching asset from `latest.json` (or directly from
   `dl.xiom-lang.org/releases/<tag>/...`), verifies `SHA256SUMS`, and
   extracts to `.toolchain/` (gitignored). `tools/validate-lessons.*`
   defaults `XIOM_BIN` to `.toolchain/bin/xiom`.
2. **`tools/generate-stdlib-ref.js`** - parses the toolchain's
   `lib/xiom/**/*.xi` and regenerates `js/stdlib-ref.js` data plus the
   module/function counts rendered in `index.html`. Removes P14 as a
   recurring task.
3. **CI workflow** in this repo (`.github/workflows/validate.yml`):
   - fetch the pinned toolchain;
   - fail if any lesson JSON is not UTF-8/ASCII;
   - compile every `solution` and `code_template` with `--check`, with a
     1-2 s per-file watchdog and the dedicated per-request work dir;
   - execute solutions with a wall-clock cap and record outputs;
   - fail on any *new* failure versus a checked-in baseline (the 185
     known failures can be baselined while they are repaired);
   - verify version metadata: `index.json.version` is generated (not
     hardcoded), `stdlib-ref` count matches the toolchain, and a
     `GET /api/version`-style value matches `TOOLCHAIN_VERSION`.
4. **Nightly drift job** against `latest.json` (not the pin) that runs
   the same lesson check and opens an issue when a new toolchain breaks
   lessons.
5. **`/api/version`** (or `health.json` generated at deploy) returning
   `{ toolchain: <tag>, stdlib: <version>, wasm: <version> }`; the UI
   footer reads it instead of hardcoded strings.
6. **WASM release asset (compiler-side, C8)**: add a
   `xiom-<tag>-wasm.tar.gz` (`xiom_wasm.js`, `xiom_wasm_bg.wasm`,
   `.d.ts`) to the release and have `fetch-toolchain` pull it alongside
   the binary. Until then, `tools/update-wasm.ps1` documents the current
   manual path and stamps `WASM_VERSION`.

## 7. Cross-repo findings (for the compiler/stdlib sessions)

These cannot be fixed in the playground repo; they are recorded here
because the playground is the consumer that exposed them.

- **C1** `xiom --version` reports `v0.58.0` for the v0.60.1 release
  (Cargo.toml not bumped; release tag not injected). Version detection
  must use the release tag/metadata.
- **C2** `xiom fmt` / `xiom format` do not exist; `xiom-fmt` is not wired
  into the CLI. Breaks `/api/format` (P4).
- **C3** Script mode ignores `--opt-level`, `--incremental`, `--parallel`,
  `--jobs`, `--timeout`, `--max-memory-mb`, `--diagnostics=json`.

Language/API changes the migration had to absorb (useful for docs and the
compiler session):

- `let mut` is gone: mutable locals are `var`.
- `for x in collection` iterates indices (Int); ranges are
  `for i in range(a, b)` and require `use xiom.iter;` (`0..n` desugars to
  `range` and needs the same import).
- `type X { ... }` requires `type X = { ... }`; `mod` is `module`; module
  functions must be `pub` to be callable through the module path; `pub use`
  re-exports are not supported.
- Method receivers are `self` / `&mut self` (no `self: &mut Self` or
  `self: &mut Box[T]`).
- Conversions moved: `int_to_str` -> `to_string` (core), `float_to_str` ->
  `convert.float_to_string`, `bool_to_str` -> `convert.bool_to_string`,
  `char_to_str`/`string.from_char` -> `to_string_char` (with
  `use xiom.convert.tostring;`), `str_length` -> `str_len`.
- `Str` has no `get(i)`: use `char_at(i)` (returns Char) or indexing; there is
  no `Str.contains` (use `string.str_index_of(s, x) != None`).
- `Set` is now the hash-set module API (`HashSet`, `hashset_new/insert/
  contains/remove`); fixed arrays are `[N]T`, not `[T; N]`; expression
  `else if` chains use `elif`; unicode escapes are `\u{...}`.
- `Option.None` / `Option.Some` constructors are plain `None` / `Some`.

New compiler findings from the migration (for the compiler session):

- **C11** Qualified nested-module struct literals do not unify with the
  module-local type (`school.students.Student{...}` vs `Student`), and a
  constructor function named through the nested path
  (`school.students.new_student`) hits `invalid redefinition of function` in
  codegen. Lessons work around both with local constructors.
- **C12** Type aliases of builtin generics (`type Row = Map[Str, Str]`) break
  method resolution (`cannot call 'insert' on this expression`).
- **C13** `.clone()` on `Str` and on struct values returns the wrong type
  (Int); lessons avoid it.
- **C14** `pub use` re-exports are unsupported (module name is then
  undefined).
- **C15** A generic `for` over `0..n` without `use xiom.iter;` reports
  `undefined variable 'range'` rather than a missing-import diagnostic.
- **C16** `--check` accepts `Option[Card]` vs `Option[Int]` mismatches only
  after the early `return None` arm is restructured, hinting at inference
  defaulting for bare `None`.
- **C17** The 31 baselined runtime failures fall into six codegen classes:
  enum payload zero-init (`store i8* 0` / `store double 0`), Vec-by-reference
  (`%struct.Vec` where `ptr` expected), `getelementptr %struct.Vec*` on a
  `Vec**`, interface dispatch (`C001: type 'Int' does not implement ...`),
  `i64` passed where `ptr` expected, and `expected '(' in call` for
  `Map[Int, Vec[Str]]` values. See `tools/lesson-baseline.json` for the full
  lesson list.

sample would make the nightly assertion flake. The skip list is generated by
the sweep and never hand-edited (`nondeterministic output` is the only reason

CI and UI:

  fails when a runnable lesson is neither expected-output-bearing nor skipped,
  when a blocked lesson carries a field, or when the skip list is stale.
- `tools/lesson-audit.js` adds an `expected` failure category when an executed
  solution does not match its stored output, so the nightly execution job
  fails on drift. A toolchain fix that changes output will surface there;
  re-run the sweep and commit the refreshed data.
- The Output tab compares a run with `expected_output` when the editor still
  holds the reference solution: "Output matches the expected result" (green),

  edited programs. Lessons without a field (blocked or nondeterministic) show
  no indicator.

Review sample (18 lessons across all levels). Two findings worth recording:

- L1-05 prints duplicated labels ("Bill:" then "Bill: $80") because the

- L2-40 legitimately prints nothing (it computes and returns), so its empty

New compiler findings from the sweep (for the compiler session):

- **C18** `Str` data that passes through `Vec`, struct fields, `Map`, or

A production incident surfaced during acceptance: every program run failed
with `cannot run '/tmp/xiom_run/...': Permission denied (os error 13)`.
Docker mounts tmpfs with `noexec` by default, and the toolchain writes and
executes compiled scripts under `/tmp`, so compose now mounts
`/tmp:size=256m,exec` (still ephemeral; every other sandbox flag unchanged).
DEPLOY.md documents why `exec` is required. This was a container-only gap:
CI runners and the WSL sweeps use ordinary filesystems, which is why no gate
caught it before the VPS did.

A second container-only performance bug was found while measuring the fixed
run: repeat runs of an unchanged program still took ~6s. Probes on the pinned
toolchain show the script cache is content-keyed and path/mtime-insensitive,
but only when `HOME` is writable: with an unwritable `HOME` (the read-only
rootfs makes `/home/xiomp` unwritable) the cache is never reused, and the
same program recompiles every time (2.9s vs 6ms in a controlled probe).
Compose now sets `HOME=/tmp/xiom-home` on the tmpfs, so repeat runs are
cache hits while edited programs still pay the cold compile (~3.5s for hello
world on a dev box, ~6s on the VPS). The compiler session should consider
making the script cache independent of `HOME` (and honoring `--opt-level` in
script mode, compiler finding C3) so cold compiles can be cheaper.

Measured cold-compile split for hello world (WSL, caches cleared, values vary
with machine load): on v0.60.1 the front-end (`--emit-ir`) takes ~0.9-1.0s
while a full `run` takes 3.5-12s, so the C backend plus clang plus link
dominate. The v0.60.1 CLI has no `--opt-level` flag at all, so the playground
cannot lower the optimization level (C3). On v0.61.0 the front-end phase
measured 3-6s even for a program that never calls `.to_str()`, suggesting the
`xiom.fmt` dependency-closure peek is paid broadly rather than only on first
conversion use; the planned reachable-function-only peek should help both
the cold-compile cost and this front-end regression.

Precise compiler-side findings from reading `crates/xiom` at the fix revision:

- R48 already salts the script cache with the compiler build identity
  (`compiler_cache_identity()`), which addresses the stale-cache report.
  Verified warm runs are 6-12ms once `HOME` is writable.
- `--opt-level` exists and is honored by the compile-only path, but the
  script-run branch (`main.rs`, `args[1] == "run"`) is handled before global
  option parsing, so `xiom run --opt-level=N` is rejected as a filename and
  `xiom --opt-level=N run f.xi` treats `run` as the source. `--run` accepts
  the flag but ignores it and compiles `a.out` uncached.
- Effect on hello world: v0.61.0 compile-only `-O0` 2.3s vs `-O2` 7.8s
  (3.4x faster); v0.60.1 shows no difference (3.8s vs 4.0s), so the win
  arrives with the v0.61.0 release. If the script-run path threads the level
  into `CompileConfig`, the level must join the cache key (or `-O0` and `-O2`
  runs would alias).

Requested, in priority order: (1) apply `--opt-level` in the script-run path
(and/or an env var the driver can set) so the playground can request `-O0`
for edit-run loops; (2) fix the broad fmt-closure peek before v0.61.0; (3)
keep the script cache independent of `HOME` if cheap; (4) add a compile-only
cache-prime mode (`run --no-exec`, or have compile-only mode populate the
script cache) so the playground can warm popular programs without executing
user or lesson code. The playground will detect the flag capability and
adopt it automatically.

Measurement harness and exact repros for the compiler lane live in
`docs/COMPILER_REPROS.md`: `tools/bench-cold-compile.js` clears the compiler
caches before every sample and reports `xiom run` and `xiom --emit-ir`
medians, with `--compare` for same-machine before/after deltas. Reference
medians there show the R55 front-end is 4-6x slower than v0.60.1 on
`--emit-ir`, largest for `to_str` (the broad fmt peek).

## 27. Crash-exit reporting and lesson semicolon compliance (2026-09-25)

### 27.1 A crashed run is no longer "ran with no output"

Relay repro (compiler lane, 2026-09-25): two mutually recursive functions
with no base case compile, then die in the XIOM runtime fault trap:

```
fn a() { b(); }
fn b() { a(); }
fn main() { a(); }
```

Measured on the mirrored v0.61.3 Linux toolchain: the driver prints
`  compiled: /tmp/xiom_run/...` and `  exit code: -1` on stderr and itself
exits 0, stdout is empty. `/api/compile` therefore reported "Program ran
with no output." with `success: true` -- indistinguishable from a real
empty run. On Windows the same program exits `0xC000001D` (-1073741795).
The same masked signature (driver exit 0, stderr `exit code: -1`, empty
stdout) appears for an out-of-bounds `Vec.get`, integer division by zero,
and `Option.unwrap()` on `None`, so this is the general runtime-fault path,
not a recursion-specific one.

Fix:

- `lib/run-xiom.js` now returns `signal` (children killed by a signal) and
  `spawnError` (spawn failures) alongside `code`; `success` additionally
  requires no signal.
- `server.js` classifies a run failure before the empty-output fallback:
  a non-zero process code, a signal, or a non-zero `exit code: N` line in
  the driver stderr becomes
  `Program crashed (exit code ...).` (`0xC000001D` renders as
  `-1073741795 / 0xC000001D`; the driver's fault sentinel stays `-1`). The
  result carries `success: false`, `runError` set and `runOutput: null`, so
  the expected-output comparison cannot match and run history records a
  failure. Partial stdout is kept and the crash line is appended.
- Compile errors, timeouts and genuine empty runs keep their existing
  messages (`Compilation failed...`, `Compilation timed out...`,
  `Program ran with no output.`).
- `tools/test-server.js` runs the repro in the execution tests (Linux/CI;
  Windows skips execution because its clang hangs at -O2). This is also the
  pointer to the queued compiler-side W002 lint: once it warns on
  unconditional cycles, this crash becomes a compile-time warning instead
  of only a runtime report.

Verification: `node tools/test-server.js` on Linux (WSL, v0.61.3): 37
passed, 0 failed, including the new crash test. End-to-end payloads from a
live server:

- crash: `{"success":false,"output":"Program crashed (exit code -1). The program died before producing output.","runError":"Program crashed (exit code -1). The program died before producing output.","runOutput":null}`
- empty: `{"success":true,"output":"Program ran with no output.","runError":null}`

### 27.2 Lesson semicolon compliance (relay guidance, verified)

Guidance (owner decision, relay 2026-09-25): `;` separates statements and
only a block's final value-producing expression may omit it. All 410
lessons' `solution` and `code_template` fields and every narrative ```xiom
fence were scanned (line-based with comments stripped; one-line and
multi-line blocks). Result: **zero unit-context statements lack `;`**; the
only non-semicolon block tails are deliberate values -- function returns
such as `self.text.clone()`, match arms like `Some(result)`, if-expression
values. L0, L1 and the L2 narratives are completely clean; the value tails
appear from L3 onward where functions return values. No lesson content
changed, so the stored `expected_output` data and the baseline stay valid;
the existing audit remains the proof at every run.

Teaching copy: L0-01 states the rule ("Every statement ends with a
semicolon"), L0-02/L0-12 repeat it in common mistakes, and L0-08/L0-10/
L0-28/L0-33 cover the if/while-condition semicolon trap. The value-tail form
first appears in L6-16 (`fn Note.read(&self) -> Str { self.text.clone() }`),
whose tips now explain that the final expression is the function's value and
therefore skips `return` and `;`. No other lesson needed a change.

## 28. Security audit: stdlib reach from submitted programs (2026-09-25)

Owner request: what can a submitted program do through the stdlib (`io`,
directory creation, process, ...) once it compiles?

### 28.1 Method

- Enumerated the v0.61.3 surface from `js/stdlib-ref.json`. The
  `playground`/`docs`/`local` tier is a reference-panel grouping only, not a
  compile-time restriction: every module in `/toolchain/lib` is reachable
  with `use`.
- Read the shipped stdlib sources (`io/io.xi`, `io/fs.xi`) and executed
  probes with the Linux v0.61.3 toolchain in WSL.
- Audited the container wiring (`docker-compose.yml`, `Dockerfile`) for what
  the server uid can reach.

### 28.2 Capabilities that work (measured)

| capability | API used | result |
|---|---|---|
| read env vars | `io.env_var("SESSION_SECRET")` | printed the secret before the fix below |
| read files | `io.read_file`, `io.fs_read_text` | regular files read fine; `/proc/*/environ` returns empty through this API because procfs reports size 0 |
| write/append files, create dirs | `io.write_file`, `io.create_dir` | works under `/tmp`; the same uid also owns `/data` |
| spawn processes | `process.spawn_command("sh", ...)` | works; ran `id -u` and wrote a file |
| network | `net.http_get`, tcp | compiles; egress is blocked by the ops `DOCKER-USER` guard (container assumption unchanged, worth re-verifying on the VPS) |
| arbitrary C | user-declared `extern "C"` + `system()` | works: `system("id -u > /tmp/f")` executed |

### 28.3 Findings

F1 (high, fixed in part) - the server environment leaked to programs. The
server inherits the compose `env_file` (`SESSION_SECRET`,
`AUTH_HELPER_KEY`, `GITHUB_CLIENT_ID`) and every compiler child inherited
the whole environment, so a one-line program could print the session secret
(measured). With `SESSION_SECRET` an attacker can forge session cookies;
`AUTH_HELPER_KEY` gives access to the host-side auth helper.

Fix landed: `server.js` spawns every compiler child with a small whitelist
(`PATH`, `HOME`, `TMPDIR`/`TEMP`, locale, `XIOM_BIN`, `XIOM_STDLIB`), so
`getenv`-based helpers no longer see server variables. `tools/test-server.js`
starts the server with a canary variable and asserts a submitted program
cannot read it (suite 38/38 on Linux, 34 + 1 Windows skip). This is defense
in depth, not a complete fix - see F3.

F2 (high, open) - the progress store is readable and writable by submitted
programs. `/data` is owned by the container uid (`Dockerfile` chowns it to
`xiomp`, uid 10001) and programs run as that same uid, so a program can list
`/data/accounts`, read every account document, overwrite it with a forged
revision, or delete it. That breaks per-account privacy and lets one user
corrupt other users' progress.

F3 (high, residual) - env scrubbing is bypassable by same-uid process
inspection. A program can spawn `/bin/sh` and read
`/proc/<ancestor>/environ` (the server's exec-time environment), which still
holds the compose secrets. Verified on the dev kernel with Yama
`ptrace_scope=1`: a child read its ancestor's exec-time environ. Since user
code can also declare its own `extern "C"` (F4), no stdlib/import filter can
prevent this. The container protects the host; it does not isolate the
server's assets from submitted code.

F4 (informational) - user code can declare `extern "C"` and call libc
(`system()` verified), so "restrict allowed modules" is not a viable
control. The container must be treated as hostile to the assets inside it.

### 28.4 Required owner/ops actions

1. Rotate `SESSION_SECRET` and `AUTH_HELPER_KEY` (rotation signs everyone
   out). Assume exposure: arbitrary code execution with the inherited
   environment has been possible for as long as the service has run.
2. Add per-execution isolation so programs cannot read the server env or
   `/data`. Options, by effort:
   - Landlock wrapper around the `xiom run` child: allow `/tmp`, `/app`
     and `/toolchain` read-only, deny `/data` and `/proc` (unprivileged,
     needs a small helper binary in the image).
   - A separate runner service/container (ephemeral per run) with its own
     uid, no `/data` mount and no server env.
3. If isolation is deferred: move the progress store and the secrets behind
   the host helper so the container holds neither multi-tenant data nor
   session secrets.

### 28.5 What is not affected

- The host: every probe ran inside the container boundary; egress stays
  blocked and `/tmp` stays a size-limited tmpfs.
- CI and the tools: the sweeps run trusted lesson code, not submissions.
- The lesson corpus: unchanged by this audit (the L6-16 tip is copy only).
